MaizeGDB Log Audit

Six days of production Apache logs, read end to end for broken pages, security exposure, and wasted work — with the findings mapped onto decisions the redesign has to make anyway.

Both logs were parsed in full — 5.66M access lines and 370,203 error lines. Two problems dominate everything else, and they are unrelated to each other. The sequence-retrieval stack is both broken (mRNA and non-coding sequence fetches never succeed) and enormously wasteful (half of all bytes MaizeGDB ships are the same index files, re-downloaded). Separately, the gene record page fans out into fifteen-plus server round-trips per view, which is the single most consequential thing the redesign can fix.

Security

Both logs · 6 findings

The headline is good: nothing in six days of logs shows a successful intrusion. The real security defects are configuration-level — the site tells attackers "yes, that exists" for every path they guess, and a legacy CMS host is drawing targeted exploit traffic.

SEC‑1

No successful exploitation found

Verified

Every injection, traversal, and webshell probe in the window was checked against its response. All of them landed on a soft-404, a real 404, a 400, or a 503 — none reached a live handler.

The clearest proof is the AcyMailing SQL injection aimed at past3: the "successful" 200 responses are 4,476 bytes, byte-identical to that host's ordinary home page. The query never executed; the attacker got the front page.

past3.maizegdb.org  200  4476 bytes   ?columns=id+FROM+%23__acym_user+AS+user+UNION+SELECT+VERSION()%23
past3.maizegdb.org  200  4476 bytes   GET /              <- same size, ordinary homepage

Similarly, the SSRF probes at 169.254.169.254 (cloud metadata) returned 400/503 from archive, and the 63 "successful" traversal hits for /etc/passwd and /.aws/credentials were all the 39 KB catch-all page described next.

SEC‑2

The main site answers 200 for pages that do not exist

High

maizegdb.org returns HTTP 200 with a ~39 KB page for essentially any nonexistent path. Of ~1,870 requests to obviously bogus paths, 1,741 (93%) got a 200; only 107 returned a real 404.

GET /etc/passwd                                200   39,290 bytes
GET /.env                                      200   39,266 bytes
GET /wp-content/plugins/hellopress/…php        200   39,346 bytes
GET /static../.aws/credentials                 200   39,294 bytes

Three consequences, in order of how much they cost you. Scanners read 200 as "endpoint exists", so MaizeGDB looks like it has thousands of live attack surfaces and keeps getting re-probed. Search engines will index junk URLs. And no uptime check or link crawler can tell a working page from a dead one, which is why broken links elsewhere in this report went unnoticed.

Fix

Return a genuine 404 status (a friendly HTML body is fine — the status line is what matters), and 410 for paths deliberately retired. Carry this into the redesign as a hard rule: status codes are part of the API contract, not decoration.

SEC‑3

Legacy CMS hosts are drawing targeted exploit traffic

High

past1, past2, past3 and archive run WordPress/Joomla stacks. past3 is being hit with the AcyMailing component SQL-injection CVE across three different route forms — this is targeted at a known vulnerable extension, not generic noise. archive.maizegdb.org meanwhile returned 4,861 × 503 — its backend fails continuously (ERR‑3), so it is only partly reachable.

These attempts fail today. They keep working only as long as the CMS never drifts out of date — which is a weaker guarantee than it sounds for hosts nobody is actively maintaining.

Fix

Snapshot these to static HTML and retire the CMS, or put them behind auth. Static archives cannot be SQL-injected.

SEC‑4

Development and staging hosts are internet-reachable

Medium

staging, sandbox, appsdev, maizedigtest, genomeqcdev, codex and claude all appear in the public access log. Separately, 1,735 requests were denied while trying to reach dev8.usda.iastate.edu through the proxy — the deny rule works, but the route is discoverable, and the block is what is holding.

Fix

IP-restrict or password-protect non-production vhosts. Given the redesign will run on claude/codex for months, worth doing before those hosts carry anything sensitive.

SEC‑5

Sustained automated scanning

Informational

Continuous background probing across the estate: ~14,600 WordPress path probes, ~13,000 .env / credential-file requests, ~2,600 webshell filename guesses (alfa.php, wso.php, xmrlpc.php), 22 Apache path-traversal RCE attempts (/cgi-bin/.%2e/…/bin/sh, the CVE-2021-41773 pattern), and one Mozi IoT-botnet dropper embedded in a request line. All rejected.

Worth stating plainly: this is normal internet background radiation for a public site, not a sign of being singled out. Fixing SEC‑2 will reduce it, because the scanners are currently being told they found something.

SEC‑6

Blind spot: 205,548 POST bodies are not logged

Limitation

An access log records the request line only. Roughly 205,000 POST requests — including BLAST_tasks.php, searchall, populate_table, and the search/gene/* handlers — carry parameters this audit cannot see. No POST-based injection can be confirmed or ruled out from these logs.

Those form handlers are the most likely place for query-parameter interpolation to survive, and they are precisely the endpoints the redesign is replacing.

Fix

Audit POST handlers by reading the source rather than the logs. In the new API, use parameterized queries everywhere and treat that as non-negotiable.

Broken on the live site

Access log · fix now

These are real user-facing failures happening today. None of them need to wait for the new site.

BRK‑1

mRNA and non-coding sequence retrieval fails 100% of the time

Critical

The FASTA service uses htslib to random-access bgzipped FASTA files over HTTP, which requires a .fai index alongside each .fa.gz. For the mRNA and non-coding files, that index was never generated — so every request fails. The correlation is absolute:

Sequence type200 OK400502Verdict
mrna057,9361,427Always fails
nc.mrna038,6952,026Always fails
nc.cdna04752,325Always fails

protein52,5095754,575Works

gene23,1154002,099Works

Confirming it from the other side: download.maizegdb.org served 99,974 × 404 for .fai requests, and the top four missing files are exactly the mRNA indexes.

34,503  404  /Zm-B73-REFERENCE-NAM-5.0/…_Zm00001eb.1.mrna.fa.gz.fai
33,529  404  /Zm-B73-REFERENCE-NAM-5.0/…_Zm00001eb.1.nc.mrna.fa.gz.fai

That is roughly 97,000 failed sequence retrievals in six days — every one a researcher who asked for an mRNA sequence and got nothing.

Fix

Run samtools faidx (and bgzip -r for the .gzi) over every .mrna and .nc.* file on download.maizegdb.org. Then add a release check that refuses to publish a .fa.gz without its index.

BRK‑2

get_sequence.php fails on nearly a third of requests

Critical

The sequence endpoint on sequence2.maizegdb.org:

200  181,657   68.2%
502   63,344   23.8%   backend died
504   21,386    8.0%   backend timed out
                ─────
     84,730 failures = 31.8%

The error log ties this to one backend endpoint: c2s2.usda.iastate.edu:29977 accounts for 115,722 proxy failures, split between connection resets (109,748 estate-wide) and hard timeouts (79,170).

What the failures are not is as informative as what they are. Three tests, all negative:

Load-dependent?    No.  Failure rate is flat 5.1–8.3% across every hour.
                        Quietest hour (18:00, 125,871 req) → 7.29%
                        Busiest  hour (22:00, 379,051 req) → 6.09%

Content-dependent? No.  Every dbtype fails at the same ~30%:
                        cdna 66.4% ok · mrna 65.9% · nuc 72.2% · protein 69.3%

Pool-member issue? No.  One endpoint only (:29977), and the 195,275 errors
                        spread evenly across all 106 proxy worker PIDs.

So this is a constant per-request failure probability against a single backend — not capacity, not a bad pool member, not a specific query. Note the direction of the load correlation is mildly inverse, which rules out saturation as the whole story.

Fix

The proxy log can localize this but cannot explain it — the answer is on c2s2 itself (accept queue, worker lifecycle, per-request crashes). Instrument there before tuning. Do not raise ProxyTimeout as a first move: it converts 502s into slow 200s and hides the signal.

BRK‑3

An internal client sends 208,272 requests with an empty gene ID

Critical

A single internal host — 2610:130:104:200:ca1f:66ff:fe5e:ee50 — makes every one of these requests, at roughly one every 2.5 seconds, around the clock. The transcript ID slot in the URL is empty, so all 203,386 answered requests return 403.

GET /fasta/fetch//https://download.maizegdb.org/…_Zm00029ab.1.cdna.fa.gz  403
                 ↑↑
          empty ID — should be /fasta/fetch/<transcript_id>/…

That same host generates 921,415 requests total — 16% of all traffic to MaizeGDB, including 116,966 hits on the fasta service root. Whatever this process is, it is stuck in a loop with an unset variable and has been for the whole window.

Fix

Identify the process on that host and fix the empty-ID case. This is the single cheapest large win in the report — it removes ~16% of total request volume for what is likely a one-line change.

What the error log adds

370,203 lines · 5 findings

The access log says which requests failed. The error log says where — it names the backend host behind every 502 and 503, which the access log cannot. It also exposes one application bug precisely, and one significant blind spot.

ERR‑1

The proteomics tab is deterministically broken for v3 gene models

Critical

Of the 5,286 HTTP 500s in the window, 2,908 come from one endpoint — and within it, from one tab. These are genuine application fatals, not proxy failures:

/record_data/gene_data.php?type=  status 500    status 200
  proteomics                            2,905        53,143
  overview                                  3        97,404
  top, annotations, expression,             0       337,614
  insertions, snps                        ────
                                        2,905  = 99.9% of this endpoint's 500s

Splitting by gene-model generation isolates it completely — every single failure is a v3 identifier:

Gene model200500Result
v3 (GRMZM / AC)6,6122,90530.5% fatal
v4 (Zm00001d)7,2980Clean
v5 (Zm00001eb)26,9590Clean

It is deterministic per gene, not intermittent — a given GRMZM gene either always fails or always works. GRMZM2G158717 (54 failures, zero successes) is a ready-made reproduction case, as are GRMZM2G472236 and GRMZM2G449909.

Fix

Load GRMZM2G158717's proteomics tab against the backend and read the PHP fatal. The shape — a subset of one gene-model generation — points at a proteomics record that is missing or malformed for older accessions, dereferenced without a guard.

ERR‑2

No application errors are captured anywhere in this log

High · observability

A strict search for PHP error signatures — PHP Fatal, Stack trace, Uncaught, on line N, mysqli_ — returns zero matches across all 370,203 lines. The log contains only proxy, authz, SSL and mod_include messages.

That is expected for a reverse proxy, but it has a real cost: the stack traces for ERR‑1's 2,905 fatals exist only on maizegdb-core3, and nothing aggregates them. The proxy can tell you a request died; it can never tell you why.

Fix

Ship the backend PHP error logs to the same place as the proxy logs. Without that, every 500 in this report is a dead end at exactly the point it becomes actionable.

ERR‑4

Access control on /data_center/reference depends on reverse DNS

Medium

1,735 requests were denied by authz_core, plus 91 authz_host failures with a revealing message:

AH01753: access check of '*.vpn.iastate.edu' to /data_center/reference
         failed, reason: unable to get the remote host name

The rule is written against a DNS wildcard, so Apache must do a double-reverse lookup on every request to decide. When the lookup fails — as it does for clients whose PTR record is missing — access is denied regardless of whether the client was legitimate. It also puts a blocking DNS query in the request path.

Fix

Replace hostname matching with IP/CIDR ranges (Require ip). Faster, and it fails predictably.

ERR‑5

TLS and protocol edge cases

Low
  • 31 SNI mismatches. 30 requests reached mgdb-proxy9 with an SNI name but no Host header; one hit usage.maizegdb.org via a bare IP with "no compatible SSL setup". The proxy hostnames are directly reachable, bypassing vhost routing.
  • 44 HTTP/0.9-style requests with no Host line, forced onto archive.maizegdb.org — all probing /admin/conf.
  • 87 malformed-URI rejections (AH10244), all the CVE-2021-41773 traversal string. Apache rejected them at parse time, which is the correct behavior and confirms the server is patched.
  • Two truncated request bodies to c2s2 (AH01097/AH02608) — the same backend as BRK‑2, failing mid-upload.

EFF‑2

Each gene page view costs 14.9 server round-trips

Critical · redesign

The gene record page loads its HTML shell, then fires a burst of independent PHP requests — one per tab — each with its own bootstrap and database connection.

gene_center HTML page loads      96,957
record_data AJAX calls        1,442,536      = 14.9 per page

One page load, one client, same second:
  00:04:49  gene_data.php?id=Zm00001eb286810&type=top
  00:04:49  gene_data.php?…&type=overview
  00:04:49  gene_data.php?…&type=annotations
  00:04:49  gene_data.php?…&type=expression
  00:04:49  gene_data.php?…&type=insertions
  00:04:49  gene_data.php?…&type=proteomics
  00:04:49  gene_data.php?…&type=snps
  00:04:49  gene_sequence_data.php?…&type=sequence

Across the four record scripts there are about twenty distinct type values. This fan-out is 69.4% of all main-site traffic (1,442,536 of 2,077,454 requests) — the gene page is not one page, it is twenty small ones in a trench coat.

It also explains BRK‑2's failure pattern. Twenty parallel requests per view, multiplied by the scrapers in EFF‑3, is what saturates the backends.

Fix

In the redesign, collapse this into one JSON call for above-the-fold content plus at most one lazy call for heavy tabs, sharing a single DB connection and letting the query planner see the whole record at once. Even a straight consolidation with no query tuning removes ~1.3M requests per six days.

EFF‑4

Transport and caching leave easy wins

Medium
  • No HTTP/2 to origin. 5,653,899 requests are HTTP/1.1; ten are HTTP/2. With EFF‑2's twenty-request burst, head-of-line blocking on a handful of connections is doing real damage.
  • 119,439 revalidations for CSS/JS that returned 304, against 37,373 full 200s. The caching works, but each 304 is still a round-trip. Content-hashed filenames plus Cache-Control: immutable would eliminate them.
  • No response times are recorded. The LogFormat has no %D, so slow-but-successful requests are invisible — this audit can identify what failed but not what was merely slow. Adding %D costs nothing and would let you measure the redesign against the current site.
  • gcv re-fetches /config/config.json on every page view (3,999 times, 6.6 KB each). Harmless, but trivially cacheable. Note: this file is legitimate — it matched a credential-file heuristic during scanning and was cleared.

What this means for the redesign

Design constraints from evidence

The gene record page is the product

Nearly 70% of main-site traffic is one page type's data layer. Whatever the new gene record page does for latency and request count will dominate every other performance decision — and conversely, no amount of work elsewhere will compensate if it ships with the same fan-out.

  1. One record, one response. Replace the ?type= fan-out with a single JSON document per record, with heavy sections (pangenome, proteomics, expression) behind one lazy call. The existing type values map cleanly onto keys in that document, so this is a re-shaping job, not a re-modelling one.
  2. Publish the API you already have. Roughly half a million requests in this window are programmatic clients pulling record_data endpoints directly. A documented, versioned, rate-limited API converts scraping load into supported usage — and gives you somewhere to point the R and Python users.
  3. Status codes are part of the contract. Real 404s, 410 for retired records, 503 with Retry-After for backend trouble. This is the fix for SEC‑2 and the prerequisite for any monitoring that works.
  4. Sequence retrieval needs an owner. Between BRK‑1, BRK‑2, BRK‑3 and EFF‑1, the sequence stack is the least healthy part of the estate: a third of requests fail, one sequence type never works, and it generates half the site's bandwidth. Local indexes and a caching layer in front of get_sequence.php would address most of it.
  5. Instrument before you migrate. Add %D to the log format now, so there is a baseline to compare the new pages against. Right now there is no way to say whether the redesign made anything faster.
  6. Retire rather than port. The past* and archive hosts, the CornCyc SSI pages and the cgi-bin scripts each carry ongoing failures. The redesign is the natural moment to snapshot them to static HTML.

Method. Full-pass parse of all 5,655,317 access log lines (zero unparsed) and all 370,203 error log lines, aggregating status, vhost, path, byte, user-agent, referer and client-IP dimensions, plus a nineteen-pattern security scan. The error log was analyzed independently for backend attribution, hourly failure-rate correlation against request volume, burst detection at one-minute resolution, and application-error capture. Every suspicious request returning 2xx was individually re-checked against response size to separate genuine exposure from the soft-404 page; heuristic matches on cm=10 (read as a command parameter) and gcv's config.json were confirmed false positives and excluded.

Limits. POST bodies are not logged, so ~205,000 form submissions could not be inspected. The log format records no response time, so slow-but-successful requests are invisible. Client IPs arrive via Cloudflare's forwarded-for chain and are not independently verified. The window is six days (23–28 Aug 2026), with 28 Aug partial — ending 13:26.
