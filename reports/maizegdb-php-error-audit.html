This log closes the loop on the last audit

The previous report identified 2,905 HTTP 500s on gene_data.php?type=proteomics, deterministic for v3 GRMZM gene models, and flagged that the stack traces existed only on the backend and were not shipped anywhere. They are in this file. The cause is a call to an undefined function unmute(), and it is still firing as of the last day of the window.

Two faults, 95% of the log

Fix first — they hide everything else

Before any individual bug is worth chasing, note that 4.6 of the 4.9 million lines come from exactly two persistent misconfigurations. Both fire on every single day of the window. Until they are fixed, this log is unreadable as an operational signal — which is presumably why the bugs below went unnoticed.

PHP‑1

A required library file has been missing for the entire window

Critical

/var/www/html/tools/sequence/include/gp_lib.php does not exist, but include/db-api.php line 15 tries to load it on every request that touches the database API. Each attempt emits two warnings:

include_once(/var/www/html/tools/sequence/include/gp_lib.php):
    Failed to open stream: No such file or directory
    in /var/www/html/include/db-api.php on line 15

include_once(): Failed opening '…/gp_lib.php' for inclusion
    (include_path='.:/usr/share/pear:/usr/share/php')

1,591,100 occurrences × 2 lines  =  3,182,203 log lines  =  65.0% of the file

Because include_once only warns, the request continues — until something calls a function that file was supposed to define. That is almost certainly what PHP‑3 below is: a call to unmute(), undefined, from code that has no idea its library never loaded.

Stated as a hypothesis, not a fact: I could not confirm that unmute() was defined in gp_lib.php — the dev host requires an interactive PIN, so I could not read the source. The two are consistent in shape and timing, and checking is a one-line grep.

Fix

Find out whether gp_lib.php was deleted, moved, or never deployed. Restore it, or delete the include_once and whatever depends on it. Then check whether unmute() starts resolving. Do this one first — it may fix PHP‑3 for free.

PHP‑2

The template engine cannot write its compiled cache

Critical · performance

Bauplan compiles .bauc templates and caches the result. lib/libbau/Loader.php line 140 cannot open those files — 1,464,192 permission failures across 77 distinct templates, every day of the window.

                        → Failed to open stream: Permission denied
                          in /var/www/html/lib/libbau/Loader.php on line 140

The megamenu partials sit on every page of the site; maizegdb-main.bauc is the master layout. So this is not a corner case — the template cache is disabled in practice, and every page render recompiles its templates from source. That cost is paid on every request MaizeGDB serves.

The relative paths (../templates/… and templates/…) are also worth noting: the loader resolves templates relative to the current working directory, so the same template is a different path depending on which script is entry point.

Fix

Give the web user write access to the template cache directory. On this host, check the SELinux context as well as the Unix mode — a correct chmod with the wrong context fails exactly like this, silently. Then confirm the .bauc files are actually being written, rather than assuming the warning's disappearance means success.

PHP‑4

User input reaches require() in the gene center router

High · security

controllers/gene_center.php:107 builds a require path from the URL segment. Arbitrary user strings demonstrably land in it — including URL-encoded Chinese text with quote and asterisk characters, which can only have come from someone pasting into the address bar:

Uncaught Error: Failed opening required 'controllers/gene_center/<SEGMENT>.php'
  in /var/www/html/controllers/gene_center.php:107
  #0 /var/www/html/controller.php(88): include()

observed <SEGMENT> values:
  ""                        327   ← trailing-slash URL /gene_center/
  id_converter                7
  sitemap / gene_list         5
  geneZm00001eb097850         5   ← malformed link, missing separator
  gene%EF%BC%89…**Translate   3   ← pasted text, quotes and asterisks
                            ───
                            369 uncaught fatals

Two things to be precise about. First, no traversal was attempted in 28 days — I checked every observed value for .., encoded dot-dot, slashes and null bytes, and found none. Second, I cannot tell from logs alone whether traversal would work; the fixed controllers/gene_center/ prefix and appended .php constrain it considerably, and Apache normalizes ../ before PHP sees the path. So this is a dangerous shape, not a demonstrated vulnerability.

It is also a plain bug: any unrecognized sub-path under /gene_center/ returns an uncaught fatal instead of a 404 — which compounds the soft-404 problem from the previous report.

Fix

Replace the dynamic require with an explicit allowlist mapping known route names to files, and return a real 404 for anything else. In the redesign, never let a request-derived string reach an include path — use a route table.

get_sequence.php in detail

The endpoint from the last report

The previous audit found this endpoint failing on 31.8% of requests and could not explain why from proxy logs. This log adds three separate defects in the same file — none of which is the whole answer, but two of which matter.

PHP‑6

Production was edited live and left syntactically broken — twice

Critical · process

All 51 parse errors in 28 days are the same file, in two tight windows on one afternoon:

20-Aug-2026 11:43    25 ×  syntax error, unexpected token "else"  … line 181
20-Aug-2026 13:10    22 ×  syntax error, unexpected token ".="    … line 180
20-Aug-2026 13:11     4 ×  syntax error, unexpected token ".="    … line 180

A PHP parse error means the file does not run at all — not a degraded response, a dead one. For roughly a minute on each occasion, every sequence request on the site failed. The two distinct syntax errors an hour and a half apart show a file being edited in place on the production host, saved mid-edit, twice.

Fix

This is a process finding, not a code one. Editing production directly also means those edits are silently reverted by the next deploy. A staging path and a syntax check (php -l) in the deploy step would have caught both.

PHP‑7

A blocking HTTP call to a sibling service sits inside the request path

High 
get_headers(https://fasta.maizegdb.org/): Failed to open stream: Connection timed out    67
get_headers(https://fasta.maizegdb.org/): Failed to open stream: HTTP request failed!    51
    in /var/www/html/tools/sequence/get_sequence.php on line 89

get_sequence.php makes a synchronous get_headers() call to fasta.maizegdb.org before doing its work. The previous audit established that the FASTA service is the least healthy component on the estate. So the sequence endpoint blocks on a health check against a service known to hang — and PHP's default socket timeout is 60 seconds, comfortably longer than the proxy's patience.

This is a plausible contributor to the 21,386 HTTP 504s the last report found on this endpoint, and it explains why failures were load-independent: the wait depends on the FASTA service's state, not on how busy the sequence server is. It is unlikely to be the whole story — only 118 of these calls timed out outright, against 84,730 failed requests — but a slow-and-succeeding get_headers() logs nothing at all.

Fix

Remove the pre-flight check, or give it an explicit short timeout and a cached result. Never make an uncached, unbounded HTTP call to another service inside a request handler.

PHP‑8

$flank is read but never set

Medium

133,379 warnings — essentially all of the "undefined variable" category — are a single variable read at six different lines of get_sequence.php:

Undefined variable $flank    line 472   79,823
                             line 487   52,875
                             line 494      311

PHP evaluates an undefined variable as null, so the flanking-sequence option silently behaves as though zero flanking bases were requested. Users asking for flanking sequence are getting output that looks valid and is not what they asked for. That is worse than an error.

Fix

Initialize $flank from the request with a validated default. Worth checking against a known record whether the feature has been quietly returning wrong output.

SEC‑9

Check whether errors are being displayed to users

Verify

Every fatal in this log is uncaught, and each carries absolute filesystem paths, function names and a full stack trace. If display_errors is on in production, all of that is being rendered into the response body for the 18,727 requests that died — a free architecture map for anyone probing the site.

I cannot determine this from the logs; it is a one-line check on the host.

Fix

Confirm display_errors=Off and log_errors=On in the production php.ini. Keep it that way in the redesign, and put a generic error page in front of uncaught exceptions.

Carry into the redesign

Design rules earned from this log

The deeper problem is that none of this was visible

A missing library file for 28 days. A disabled template cache on every page render. 15,623 fatals on one gene tab. None of it surfaced, because 170,000 errors a day is the normal background and nobody can read that. The redesign's error handling matters more than any single bug below.

  1. Treat warnings as failures in development. Both 95%-of-the-log faults are warnings, not errors — the application ran "fine" while missing a library and recompiling every template. Run the new stack at E_ALL with warnings escalated in CI, so this class of fault cannot reach production silently.
  2. Never build an include path from a request. PHP‑4's dynamic require should be an explicit route table. This is the single highest-risk pattern in the current codebase.
  3. Fail per section, not per page. Most fatals here kill an entire record page because one panel hit a null. The new record API should return partial data with a per-section error, matching the tabbed structure the previous report recommended consolidating.
  4. No synchronous calls to sibling services in a request handler. PHP‑7 puts an unbounded HTTP call to the least reliable service on the estate inside the sequence path. Cache, timeout, or drop such checks.
  5. Verify the template cache is actually writing. Bauplan's cache has been silently disabled for at least 28 days. Whatever the new stack uses, add a startup assertion that the cache directory is writable rather than trusting a warning to be noticed.
  6. Ship application errors somewhere a human sees them. The previous audit flagged that backend PHP traces were not aggregated. This file proves the cost: the answer to that report's biggest open question was sitting in a log nobody was reading.
  7. Stop editing production. PHP‑6 caught it happening twice in one afternoon. A php -l gate and a staging path would have prevented both outages, and would also stop live edits being silently reverted by the next deploy.

Method. Full parse of all 4,893,529 lines (4,801,080 timestamped entries plus 92,449 stack-trace continuations). Messages were normalized — numbers and quoted strings replaced with placeholders, the in FILE on line N suffix split off — then grouped by pattern and by emitting location, giving the counts above. Fatals were grouped separately and their stack traces read. Security signatures for SQL errors, dangerous sinks, traversal and file inclusion were searched across the raw file.

Limits. This log records errors, not requests — it has no URLs, client IPs, or response codes, so findings here cannot be attributed to individual users or joined to the access log except by inference (as done for PHP‑3, where counts and behavior match). Successful-but-wrong behavior leaves no trace: a silently null $flank appears here only because PHP happens to warn. The unmute()/gp_lib.php link is a hypothesis — the dev host requires interactive authentication, so I could not read the source to confirm it. Window is 3–31 Aug 2026; the access-log audit covered 23–28 Aug, so the two overlap by six days.
